## 2026-10-20 — Owner-approved DSL choices
1. **Scenario ids** use `[a-z][a-z0-9-]{0,39}`. The spec's `ID` rule (`[a-z][a-z0-9_]{0,15}`) applies to variables only; the spec was wrong for scenario ids (`non-repeatable-read` is 19 chars with hyphens).

## 2026-10-20 — P2–P4 engine: deviations from the spec and guesses
Nothing in §4 was changed, and `expected.json` and the goldens were never edited to make a test pass. Everything below is either additive or a spec gap.

**Trace schema (§5.8 is an "e.g." shape; additions are backward compatible)**
- Events carry extra optional fields `reason` (abort/skip/block reason code) and `blockedOn`. A user `ABORT` event has status `aborted`, reason `abort_user`.
- `storeAfter` lists the full store after every event (not a delta). Largest canned trace is under 7 KB, so the 20 KB budget holds. A 200-step, 64-key playground trace can be large; revisit if the UI needs it.
- `snapshotTS` is 0 until a transaction's first data operation (and at RU/RC). `stmtTS` is the clock at the start of a READ/SCAN/PUT/DELETE and 0 for other ops.
- `reads` has one entry for the version the reader saw (or `absent`), then one entry per version it could not see (`invisible_*`). `rw_edge` effects also carry `reason: rw_edge_added`.
- Steps queued behind a blocked statement that are later discarded because the transaction aborted are emitted as `skipped` events with `resumed: true`.
- Canonical JSON: keys sorted, HTML escaping off, `\n` never emitted. Digest = SHA-256 hex of the canonical JSON without the digest field.
- JSON Schema validation uses a small in-repo validator (stdlib only) covering exactly the keywords `trace.schema.json` uses.

**Semantics left open by the spec (guesses)**
- A doomed transaction that issues an explicit `ABORT` records `abort_user`, not `abort_dependencies` (it is rolled back either way).
- `expected.json` `mechanism` is derived as: first engine-initiated abort reason if any, else `visibility` when the invariant holds, else `none`. This reproduces all 32 cells.
- An invariant over an unbound variable is `n/a` (spec), also when the cause is an arithmetic range error.
- SIREAD lock choice for the `via` label of a rule-3 edge: an exact key lock wins over a prefix lock; among prefixes the lexicographically first.
- Rule 1/2 edge sources are all writers of versions that are uncommitted or committed after the reader's snapshot (one edge per writer, deduplicated).

**Structure**
- Added packages `engine/gen` (schedule generator, splitmix64) and `engine/matrix` (matrix compute/diff). `oracle/detectors.go` was not needed and does not exist. `run.Exec` additionally returns the manager so tests can check store invariants.
- `ssi.Fault` is a package-level struct of test-only fault switches (AC4.3). It is never set outside tests.
- Property tests sample the expensive P1 checks: schema validation every 25th schedule, digest re-run every 10th, mid-run chain shape every 10th. All other properties run on every schedule.

**Mutation checks (AC4.3) — honest result**
Disabling edge rules 1, 2 and 3 is caught by random schedules or canned scenarios (rule 3 breaks write-skew and read-only-anomaly) and shrinks to 8 steps. Disabling the commit-time check or the after-commit re-check is *not* visible to serializability checks: a dangerous structure can only appear when an edge is added or when O commits, and both moments are checked, so each of those two rules is redundant for correctness (defense in depth). They are covered by targeted tests (`commitCheckSeesDanger`, `afterCommitDoomsImmediately`): the after-commit re-check dooms the pivot at its next operation instead of at COMMIT.
## 2026-10-20 — P5: toolchain pin, store deltas, WASM
**Toolchain.** `go.mod` now has `go 1.22` and `toolchain go1.27.0`. `wasm_exec.js` is copied from the same toolchain: `C:\Program Files\Go\lib\wasm\wasm_exec.js` (Go 1.24+ keeps it in `lib/wasm`; `tools/buildwasm` also checks `misc/wasm` for older toolchains). Its SHA-256 is recorded in `engine.json` and checked by a test against the toolchain's copy. Node v22.16.0 / npm 10.8.3 were already installed.

**Trace size (owner condition 2).** A near-worst-case schedule allowed by the limits (64 keys, 198 steps, 3 transactions each writing all 64 keys with two blocked behind the first, 8 KB source) produced a 3,341,036 B trace with a full `storeAfter` on every event (327 events). That exceeded 1 MB, so `storeAfter` is now a *delta*: only the keys the event changed, each with its complete chain (an empty chain means the key was removed). Every 32nd event (index % 32 == 0) additionally carries `storeFull`, the whole store, so the UI can seek without replaying from the start; `trace.Replayer` rebuilds the state. The same schedule now measures **288,091 B** (RU/RC) and 193,710 B (SI/SER); `TestWorstCaseTraceSize` fails above 1 MiB. The constructed schedule uses 3 transactions rather than 6; it was chosen to maximise events times store width, not to exhaust every limit simultaneously. The 32 committed goldens were regenerated and verified to differ from the old ones only in `storeAfter`, `storeFull` and `digest`.

**WASM (AC0.1 re-measure with the real engine).** `GOOS=js GOARCH=wasm CGO_ENABLED=0`, `-trimpath -ldflags="-s -w -buildid="`, `GOFLAGS=-mod=readonly`: **5,170,206 B raw, 1,428,460 B gzip (-9)**, SHA-256 `7ffc34bf...`. This is under the 1.5 MB CI gate but over the 1.0 MB target, with a margin of only about 71 KB. Cause measured with probe modules: `encoding/json` (through `reflect`) alone adds about 2.4 MB raw / 635 KB gzip to a Go WASM binary (hello-world 1.97 MB raw / 584 KB gzip; hello plus `encoding/json` 4.37 MB / 1.22 MB; plus `fmt` 2.45 MB / 716 KB). Removing `encoding/json` from the WASM path (hand-written canonical encoder for the trace types, schema validator kept out of the WASM build) would recover roughly 600 KB gzip. Not done: it is a contained but non-trivial rewrite and the gate is not failed, so it is left for the owner to decide.

**Reproducibility.** `TestBuildIsReproducible` builds twice, the second time with an empty `GOCACHE` (a cache hit would make the comparison meaningless), and requires identical SHA-256. `TestCommittedEngineMatchesSource` rebuilds and compares with the committed `engine.json`, WASM and `wasm_exec.js`.

**Interpretation of "no web/ code".** Only the engine artifacts the spec assigns to P5 live under `web/public/` (`engine/worker.js`, `engine/client.mjs`, `engine/engine.json`, hashed `.wasm`, `wasm_exec.js`, and generated `traces/`). No Next.js app code exists. The 2 s timeout lives in `client.mjs` (main-thread side, as the spec describes); `worker.js` removes `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, `importScripts` and `WebTransport` after loading. Header-level CSP for the worker is a P0/AC0.2 item for the owner.

**Tooling.** staticcheck v0.8.2 was installed locally (`go install honnef.co/go/tools/cmd/staticcheck@latest`, outside the repo) and is clean. gcc (MinGW-W64 15.2) is present, so `go test -race` works locally.

**Added beyond the spec.** `scripts/fixtures/random-digests.json`: native digests of 100 random schedules x 4 levels, compared with the WASM digests under Node, in addition to the 32 canned traces. `engine/run/check.go` holds the property checks so that `azoo gen` and the tests share them.

## 2026-10-20 — WASM hash made independent of commit and OS (`-buildvcs=false`)
CI failed on its first run: `TestCommittedEngineMatchesSource` rebuilt `81fae0fc...` against the committed `7ffc34bf...`. Cause (found by extracting the build info embedded in the Windows and Linux binaries and diffing their sections): by default (`-buildvcs=auto`) Go stamps the main module's pseudo-version, which contains the HEAD commit time and hash and a `+dirty` marker, into the binary (`mod github.com/Aditya-tec/anomaly-zoo v0.0.0-20261020144759-bed8f75c2812+dirty` in the committed file). So the hash changed with every commit and with working-tree state; it was not a Windows-vs-Linux effect. Every earlier local pass happened while HEAD stayed at `bed8f75` with a dirty tree. Evidence: with `-buildvcs=false` a Windows build and a Linux CI build (Go 1.27.0 both) are byte-identical, `2249ad7fb38b3570533757a3d8d37d15f23e5acb148bc8199d9a391481bf024e`, 5,170,020 B.

Owner chose option A: `tools/buildwasm` now builds with `go build -mod=readonly -trimpath -buildvcs=false "-ldflags=-s -w -buildid=" ./cmd/wasm` (env `CGO_ENABLED=0 GOOS=js GOARCH=wasm GOFLAGS=-mod=readonly`). The committed binary is `azoo.2249ad7f.wasm` (5,170,020 B raw, 1,428,516 B gzip by Go `compress/gzip` best). `TestBuildIsReproducible` now also fails if the binary contains the module pseudo-version or `vcs.revision`. The earlier entries above that quote `7ffc34bf` and 5,170,206 B describe the superseded build; sizes are within 0.01 % of the new ones. The brotli figure for the new file is in the next line.Brotli quality 11 of the new file: 1,044,049 B (gzip -9 via Node zlib: 1,420,852 B).

## 2026-10-20 — Vercel build failure: `NEXT_NO_ROUTES_MANIFEST` (spike/vercel.json)
First Vercel build of the spike (commit `e4628e6`): install, `prepare`, `next build`, CSP injection and CSP verification all succeeded (3 pages, 9 hashes), then Vercel failed with `The file "/vercel/path0/spike/out/routes-manifest.json" couldn't be found`. Cause: `spike/vercel.json` had `"outputDirectory": "out"`. Reading the bundled `@vercel/next` builder (CLI 64.5.0): with the Next.js framework preset, `outputDirectory` is Next's `distDir` (`config.outputDirectory || ".next"`), from which it reads `routes-manifest.json`; for a static export it locates `out/` itself via `.next/export-detail.json` (which our build writes: `{"version":1,"outDirectory":".../spike/out","success":true}`). So the correct setting is no `outputDirectory` at all. Fixed by removing that line; the spec §11.2 "[VERIFY] static-export build is served from `out/`" item is therefore: yes, automatically, with the default Output Directory. Not verified on Vercel itself yet (the agent could not run the Vercel CLI locally: it fails with `spawn cmd.exe ENOENT` in this environment). The fallback in docs/P0-CHECKLIST.md was also corrected (it needs the Other preset, where Output Directory is a plain folder).

## 2026-10-20 — P6: web/ (Next.js static export): decisions, deviations and guesses
Spec §12 P6, §7, §8, §9.6, §10. Spike left untouched; `web/` is the real app. Stack: Next 16.4.2, React 19.3.1, TypeScript 5.9.3 strict (plus `noUncheckedIndexedAccess`), Tailwind 4.3.3, 3 production dependencies (next, react, react-dom), exact pins, lockfile committed, `npm ci --ignore-scripts`.

**Tooling versions and why**
- TypeScript 5.9.3, not 7.0.2: 7.x is the new native compiler port; typescript-eslint and Next expect the JS compiler API.
- Vitest 5.0.3 (Vite 8 / Oxc), generated with an ephemeral `npx npm@11` lockfile: npm 10.8.3's resolver crashes ("Cannot read properties of null (reading 'edgesOut')") on any dependency tree containing Vitest 4/5, even in an empty project. Vitest 3.2.7, which resolves fine with npm 10.8.3, carries two critical advisories (tinypool RCE gadget, @vitest/mocker path traversal) fixed only in 4.1.11+/5.x. `npm ci` with npm 10.8.3 installs the npm-11-generated lockfile correctly; CI's Node 22 ships a newer npm anyway. `npm audit` (dev and prod): 0 vulnerabilities.
- Lighthouse: plain `lighthouse@13.5.0` + `chrome-launcher@1.2.1` and my own `scripts/lighthouse-check.mjs`, instead of `@lhci/cli@0.15.1`, whose pinned old Lighthouse and puppeteer/proxy chain accounted for most of 20 advisories (2 critical, 11 high) in the dev tree. lighthouse 13.5.0 declares `node >=22.19`; local Node is 22.16.0 and it ran fine (npm only warns); CI uses the current Node 22.
- ESLint 9.39.5 (npm prints a "no longer supported" deprecation; ESLint 10 was not adopted to stay compatible with the other pins). All pins are at least two weeks old except `next`/`react`/`react-dom` (patched releases, see the spike entry).
- `eslint-plugin-react-hooks` 7.1.1 with only `rules-of-hooks` and `exhaustive-deps` enabled (not its newer compiler rules).

**Routing, headers, hosting**
- `web/vercel.json`: `"framework": null`, `"outputDirectory": "out"` (the combination proven by the spike), plus **`"cleanUrls": true`** (new): the export writes `about.html` and `anomalies/<slug>.html`; without clean URLs a static host would 404 `/about`. Header rules are copied from the spike: non-overlapping sources, values exactly as §10.2.
- **Plain `<a>` links instead of `next/link`.** With `next/link` the client router prefetches and navigates by requesting `/about/__next.about.__PAGE__.txt`, but the static export writes `about/__next.about/__PAGE__.txt`; every such request 404s on a plain static host (it recovers with a full navigation, but logs console errors, which the CSP smoke test and Lighthouse best-practices treat as failures). Normal page loads are the robust choice for a fully static site; it also stopped Next from prefetching 36 pages from the home page. Side effect: page changes are full loads, not client transitions.
- `scripts/serve.mjs` (local server used by Playwright, Lighthouse and `check-deployed.mjs`) applies `vercel.json` headers, serves `404.html` with status 404, and now compresses text with brotli/gzip like Vercel does. Without compression Lighthouse (simulated mobile) measured performance 0.85-0.87 and 571 KB transferred; with it 0.99-1.00 and 142 KB. The compressed numbers are the ones that model production; whether Vercel serves brotli to browsers is part of the deployed check (`check-deployed.mjs` fails on an uncompressed page).
- Sitemap and robots via Next metadata routes (`app/sitemap.ts`, `app/robots.ts`, force-static); canonical site URL constant `https://anomaly-zoo.vercel.app` in `lib/data.ts`. `/playground` is not in the sitemap, navigation or any link. `/og/[slug]` is P7 and not built.

**Data and rendering**
- Pages read `public/traces/manifest.json` and the trace files at build time (server components, `lib/data.ts`), verify each file's sha256 and digest against the manifest, and embed the four traces of an anomaly in its HTML. The browser never fetches trace JSON in P6. HTML is 5-9 KB gzip per page (57 KB raw for an anomaly page, which includes the four traces).
- Home data budget ("≤ 10 KB"): the map is built from a trimmed `HomeData` (3 KB) derived from the manifest; `matrix.json` is 3,090 B; a unit test caps both at 10 KB. The full manifest (11,300 B raw) is read at build time only.
- Store panel: `lib/replay.ts` rebuilds the store at any step from `storeAfter` deltas and the `storeFull` snapshots every 32nd event; a unit test checks it equals the delta-only replay at all 308 (trace, step) pairs and that the last step reproduces `finalState`.
- "Step N of M" counts engine **events** (a blocked statement and its resumed run are two events), not lines of the script.
- Default level of an anomaly page = the highest level at which its invariant is still violated, computed from the manifest (Dirty Read RU, Lost Update RC, Write Skew SI, Deadlock SER). Guess (the spec's §7.4 example implies it). Switching level keeps the same step (clamped); Reset returns to step 0. URL: `?level=SI&step=5`, read after mount, written with `history.replaceState`; out-of-range or malformed values are ignored.
- Result banner, map cells, level-switch chips, compare strip and verdict are all produced by `lib/outcomes.ts`. The outcome words exist only in that file. Enforced three ways: an ESLint rule (`no-restricted-syntax` on string literals, template text and JSX text, exempting only `lib/outcomes.ts` and tests), a unit test that scans the source text, and a unit test that runs the real ESLint config on snippets (fails if the rule is weakened). Another unit test checks all 32 manifest cells against the Go engine's `scenarios/expected.json` and that flipping a manifest cell flips the label.
- The PostgreSQL badge component exists and renders nothing (flag `SHOW_PG_BADGE = false`; tested). The About conformance section is guarded by `SHOW_CONFORMANCE_SECTION = false` and is not in the HTML. No route contains the string "postgres" (e2e test).
- Hook line = the scenario title (≤ 12 words); no separate hook was invented. The spec's §8.2 footnote, `[VERIFY]` PostgreSQL statements and limit-3/limit-4 PostgreSQL clauses were not shipped; see docs/COPY-TODO.md for every piece of copy that is mine.

**Security and privacy**

## 2026-10-21 — P8: PostgreSQL conformance (decisions and guesses)
Spec §9.4, §12 P8. Numbers live in `web/public/conformance.json` and `docs/METHODOLOGY.md`; this entry records the choices I made where the spec or the task did not decide.

**D-P8-1. `k text COLLATE "C"`.** The spec's table is `kv(k text primary key, v bigint not null)`. With the cluster's default locale (the official image uses `en_US.utf8`) `ORDER BY k` is not byte order, while the engine sorts keys bytewise and `starts_with` is bytewise. I declared the column `COLLATE "C"` so the comparison does not depend on the cluster's locale. No scenario or generated key is affected today (keys are `[a-z0-9:._-]`), so this only removes a way for the harness to be wrong.
**D-P8-2. pgx query mode.** `QueryExecModeExec` (extended protocol, no prepared-statement cache) so that a cached prepared statement never interacts with an aborted transaction. The SQL text is exactly the spec's, with no casts.
**D-P8-3. Parallel workers, one schema each.** The spec says the table is truncated per run, which is sequential. 500 schedules x 3 levels is about 1,500 runs and a blocked statement costs 200 ms, so I run N workers, each with its own schema (`az_w0` ...) and its own `kv`. CI uses 4, the nightly 6. Schedules never share a table, so results do not depend on N (the canned scenarios run on one worker).
**D-P8-4. Blocked-statement bookkeeping.** The spec fixes 200 ms, the `wait_event_type = 'Lock'` test and the 2 s unblock wait. Mine: poll every 5 ms; a blocked statement counts as *still blocked* only after it has kept waiting on a lock for 60 ms past the last commit/abort/error; a statement that is neither done nor lock-waiting after 10 s is cancelled and recorded as an anomaly; at the end of the schedule blocked statements are cancelled with `pg_cancel_backend` (the engine's `blocked_at_end`).
**D-P8-5. A scripted ABORT is a successful statement on both sides.** The engine records `ABORT` as an event with status `aborted` and reason `abort_user`; the harness maps that to "ok" (a harness bug found by the first canned run, not an engine bug).
**D-P8-6. Seeds.** Random schedule `i` uses seed `8000000 + i` at every level, so the same 500 schedules run at RC, SI and SER, and the nightly 10,000 is a superset. `gen.Config.NoDelete` (new, engine commit of its own) turns the generator's DELETE draws into READs; schedules for a given seed differ from the default ones, and with the option off nothing changes (random-digest fixture).
**D-P8-7. What counts as a mismatch.** Decided on the first PostgreSQL run of a (schedule, level): strict `Diff` (statement status and abort class, READ/SCAN results, written values, final state, set of system-aborted transactions); for a schedule where either side has a deadlock victim only "both sides have one". The 5 (or 30) re-runs classify it; they do not change whether it counts.
**D-P8-8. "Simultaneous blocking" (`RaceRisk`).** While measuring I found that PostgreSQL's own history for a schedule varies from run to run, and that this happens only in schedules where at least two statements were blocked at the same time (single-waiter schedules were identical in 100/100 runs at all three levels). The harness therefore flags a PostgreSQL run in which a statement became blocked while another was already blocked, re-runs such schedules 5 times even when the first run agreed, and re-runs mismatching ones 30 times. This is a measurement of PostgreSQL's variation, not a way to hide mismatches: such a schedule still counts as a mismatch on the run that mismatched, the report prints the identical rate among schedules **without** simultaneous blocking, and an unstable mismatch **without** it fails the harness.
**D-P8-9. Divergence matching by signature** (`conformance/divergences.json`, `Signature` in `report.go`): level, SER abort-set kind, `race/varies` or `race/fixed`, and the kinds of difference seen. Coarse on purpose; the guard against it hiding a bug is the no-simultaneous-blocking rate and `unexplained == 0` (see METHODOLOGY.md).
**D-P8-10. SER buckets by count.** "Engine aborts more" is `|E| > |P|`, "fewer" `|E| < |P|`; equal counts with different sets are reported as their own bucket instead of being forced into either.
**D-P8-11. Read Uncommitted.** Not compared (spec §9.4), but the harness asks PostgreSQL for `READ UNCOMMITTED` on the dirty-read schedule and records whether a dirty read happened and whether the history equals `READ COMMITTED`'s. The site says "PostgreSQL has no read-uncommitted" only if that probe saw no dirty read (the sentence is the task's; the proof is the probe).
**D-P8-12. Local PostgreSQL for development.** The Docker daemon was not available on the development machine, so I used the portable EnterpriseDB build of PostgreSQL 16.15 (the version CI's `postgres:16` image reports). It was downloaded to a scratch directory outside the repository; nothing from it is committed. The numbers committed come from the CI run on the `postgres:16` service container.
**D-P8-13. CI gating.** The conformance job fails if: a canned outcome differs from PostgreSQL and is not covered by a divergence; a mismatch has no simultaneous blocking yet did not reproduce; any mismatch is unexplained; either side has a non-serializable SER history; the Read Uncommitted probe is missing. Abort-set differences at SER do not fail by themselves; they are the reported statistics.
**D-P8-14. Nightly.** `conformance-nightly.yml`: `schedule` (03:23 UTC) and `workflow_dispatch` with a numeric `schedules` input (default 10000, passed through `env` and validated, never interpolated into the script), 6 workers, 345-minute timeout (hosted limit 360), `contents: read` only, report uploaded with `if: always()`. I did not dispatch it (the token cannot, and the task says the owner does).

**D-P8-14 (revised).** The extrapolated single-job nightly (~4 h) was too close to GitHub's 6 h limit, so `conformance-nightly.yml` is now a matrix of three shards (RC, SI, SER), each with its own `postgres:16` container, `timeout-minutes: 300`, the same fixed seed range (8000000 .. 8000000 + schedules - 1), then a `merged report` job (`azoo-conformance -merge`) that fails if a shard report is missing. Shards pass `-rerun-race=false`, so only actual mismatches are re-run (5x); the extra re-runs of matching schedules with simultaneous blocking, which CI does to measure PostgreSQL's variation, are skipped. Trigger is weekly (Mondays 03:23 UTC) plus `workflow_dispatch`. Dispatch name: **conformance-nightly**.

## 2026-10-22 — Terminal UI re-skin
**D-UI-1. Dark is the default for every visitor, regardless of the operating-system setting.** The site is a phosphor terminal (near-black, green, amber for focus and warnings, red for errors). The `prefers-color-scheme` block is gone; `tests/contrast.test.ts` now fails if one comes back.
**D-UI-2. "Paper" is an opt-in light variant.** The theme button switches Phosphor and Paper; Paper (`data-theme="light"`, remembered in `localStorage` under `azoo-theme`) keeps the same monospace, square-cornered look in dark green on paper for bright rooms. It replaces the old System, Light, Dark cycle. Both themes are held to 4.5:1 for text and 3:1 for borders and focus rings by the contrast test, and axe scans both.
**D-UI-3. System monospace stack, no web font.** The privacy rule (no third-party requests, a CSP with no font sources) stands. The stack names JetBrains Mono and Fira Code first, so they are used when installed, then the platform's monospace faces.
**D-UI-4. Scanlines are a tiled background on the page, not an overlay.** A fixed full-screen overlay, and the same gradient on every window, made WebKit hydrate more slowly and repaint under scroll. One small tiled background on `html` costs nothing and still gives the backdrop a CRT texture. Cards are opaque, so the lines show only on the page background.
**D-UI-5. Decorative shell text is either a real command or clearly a comment.** The hero types `azoo matrix scenarios`, which exists (`azoo --help`) and prints the same matrix as the map below it. Other furniture is styled as comments (`// mechanism`, `// end of page`) or is part of the brand prompt, and is hidden from assistive technology.
**D-UI-6. Glow is for headings, the logo and the brand only.** Paragraphs, lists, tables, code and summaries never carry it (`e2e/terminal.spec.ts` checks computed styles on the home, About and anomaly pages), so long pages stay crisp. There is no glow animation; the only animations are the one-time hero typing and the blinking cursor, and `prefers-reduced-motion` turns both off (tested).
**D-UI-7. Headings are capitalised by CSS.** The DOM text stays in sentence case (tested), so screen readers, search and copy-paste see the real wording. Side effect: `innerText` is upper case, so the framing test in `e2e/csp.spec.ts` matches case-insensitively.
**D-UI-8. The playground editor is read-only until hydration.** Root cause of the WebKit playground flake: the server-rendered textarea is editable before React hydrates, and hydration resets it to the default scenario. Anything typed in that window is lost, for a real visitor as well as for the tests (reproduced in Chromium by holding back the scripts, typing, then releasing them). The editor is now `readOnly` until hydrated and carries `data-hydrated`; Playwright's `fill` waits for an editable field, so the race is gone from the tests too. The baseline (before the re-skin) flaked at a similar rate for the same reason.
**D-UI-9. The level meter counts, it does not claim.** Its heading is "This engine, by level" and each row reads "holds in n of N", counted from the habitat-map cells. The bar is `aria-hidden` and the count beside it is the text equivalent.
